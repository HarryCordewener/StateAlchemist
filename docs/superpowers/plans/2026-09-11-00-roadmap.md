# StateAlchemist roadmap

**Spec:** [`../specs/2026-09-11-statealchemist-design.md`](../specs/2026-09-11-statealchemist-design.md) ·
**Docs:** [`../../index.md`](../../index.md)

The order of work is chosen so architectural problems surface while they are cheap to fix:

1. **Documentation first.** The user docs describe the library as designed. They are the contract every later
   step is checked against, and the first place a design problem shows: if a behaviour is hard to explain, it is
   wrong.
2. **Interface-based tests next.** The semantics become tests written against `IMachine<TValue>` — not against
   any implementation — and run first against a slow, obviously-correct **reference interpreter**.
3. **The generator last.** It is built to make the same contract suite pass. A generated machine that disagrees
   with the interpreter fails the same test.

The code of every validated plan is on `main`, one commit per plan, so the repository always holds what the plans
say. Publishing a package is a decision for its time, not a step of any plan.

Each plan argues from the types and lessons of the one before it, so none is written against guesses: its code is
first built and tested on top of the previous plans' validated tree, and only then written down. A plan counts as
validated when its files, extracted from the plan text alone on top of the earlier plans, build and pass. The gates
below remain review stops before *executing* the next plan.

## How the tests are layered

| Layer | Tests | Catches |
|---|---|---|
| Public API | A snapshot of the runtime's entire public surface (PublicApiGenerator + Verify) | Any unintended API change, in review |
| Model | Unit tests of the analysis on small hand-built trees | Wrong semantics — LCA, roles, precedence, conflicts — with no machine involved |
| Contract | One suite against `IMachine<TValue>`, inherited by a test project per implementation (`[InheritsTests]`) | Any implementation that disagrees with the docs |
| Allocation and benchmarks | `GC.GetAllocatedBytesForCurrentThread` tests on every synchronous path; BenchmarkDotNet against Stateless and a hand-written `switch` | Performance regressions |

## Gates

Each gate is a stop for review before the next plan is written.

- **After documentation:** the docs read as a library you would want to use; every concept is explained without
  hand-waving.
- **After Plan 1:** the model's API and the analysis tests settle every rule in the docs. Anything the model cannot
  express is a design change, made in the spec and docs first.
- **After Plan 2:** the contract suite passes on the reference interpreter, and the TNC-shaped sample machine
  expresses every pattern TNC needs.
- **After Plan 3:** decisions, deferral and concurrency behave as documented under test, including cancellation and
  backpressure against a real `Pipe`.
- **After Plan 4:** generated machines pass the Plan 2 contract suite and agree with the interpreter on random
  machines; the generated code reads as spec §7 describes it.
- **After Plan 5:** the same for Plan 3's contracts.
- **After Plan 6:** every performance target in spec §9 is met.

## Findings from validating Plan 1

Building Plan 1's first tasks in a scratch copy surfaced these; the plan already reflects them.

- **`dotnet sln add` needs `--include-references false`** on the .NET 11 SDK. It otherwise re-adds referenced
  projects and fails with "Solution folder 'src' already contains a project".
- **Verify tags *received* snapshots by framework** (`RuntimeApi.DotNet11_0.received.txt`) while the *verified*
  file is shared. Accept by renaming one received file to `RuntimeApi.verified.txt`.
- **`dotnet new tool-manifest` writes `dotnet-tools.json` at the repository root** on this SDK, not in `.config/`.
- **MarkdownSnippets** needs `"ExcludeMarkdownDirectories": ["superpowers"]` (a directory *name*) in
  `mdsnippets.json` to leave specs and plans alone; the command-line flag did not work.
- **A transition method named like a constant it uses** (`Will` with `[On(Will)]`) breaks the attribute. Now in
  the docs as a pitfall.
- **Role consistency is per binding, not per role.** A transition declared on a parent may name a state if it
  *binds* the same way from every leaf. The first rule compared raw roles and wrongly refused `ref Naws` on a
  transition into `Naws` from its parent. Fixed in the spec and docs.

## Findings from validating Plan 2

Running the contract suite on the reference interpreter surfaced these; the spec and docs already reflect them.

- **A state being started over is active when step 2 resets it**, so its snapshot is taken first and put back if
  the transform throws. Spec §6.2 had claimed step 2 only touches inactive slots.
- **`SALCH0301` does not apply to the root**: re-entering it clears nothing.
- **`Enqueue` outside a transition throws**, and **`StartAsync` twice throws** — both previously undefined.
- **Events queued before a rethrow run before the next trigger.**

## Findings from validating Plan 3

The decision, backpressure, run and concurrency contracts surfaced these; the spec and docs already reflect them.

- **`DecisionFailed` is a runtime type**, not generated: a module declares its recovery before any machine exists.
- **The pending state sits below the active leaf** (a decision plans as a stay); decisions' `Decide` and per-outcome
  `Completed` are now role-checked the way they run.
- **A failed decision — `Decide` or `DecideAsync` — fires `DecisionFailed` from the leaf after the pending state
  ends.** Events that waited run when the decision resolves, before the rest of the paused input.
- **A batch that throws** stops there and cancels a decision it started.
- **Self-firing is caught in every transition while a decision is pending**, at no cost otherwise; `Enqueue` from a
  decision must start processing, because the machine is idle while a decision runs.
- **The generated machine's inbox design works for every mode**: the interpreter uses it throughout, with the
  modes differing only in what they refuse.

## Findings from validating Plan 4

- **Plans 4–7 are re-cut.** Actions, events, lifecycle, hooks and exceptions moved into Plan 4: nearly every
  contract machine has actions, so a generator without them could not be held to the suite. Performance became its
  own plan (6), so Plan 5 is about semantics alone.
- **Roslyn cannot see a referenced assembly's non-public members**, so the declaring-library diagnostics need an
  analyzer where the module is written (Plan 7).
- **Generated code is plain C# 7.3**, compiled in a test at that version with every warning reported.

## Outlines for Plans 5–7

These become full plans at their turn; listed here so the whole shape is visible.

- **Plan 5 — decisions, deferral, runs, `Serialized` (generator).** The pending slot owning a
  `CancellationTokenSource`; outcomes read from the union by pattern; `DecisionFailed`; the inbox the interpreter
  uses, generated around a `Channel` (bounded with `InboxCapacity`); the self-fire `AsyncLocal` in decisions and
  while pending; runs by stop set, generated as a scan. Plan 3's contracts and the random-machine agreement,
  extended to decisions and runs, pass against generated machines.
- **Plan 6 — performance.** Explicit `IsCompletedSuccessfully` fast paths instead of `async` wrappers;
  `PoolingAsyncValueTaskMethodBuilder` on `net8.0`+; `SearchValues` for runs with a scalar fallback; "not started"
  and "stopped" as dispatch states; synchronous `Fire` where nothing is async (`SALCH0601`); allocation tests on every
  synchronous path; BenchmarkDotNet against Stateless and a hand-written `switch`; generator time on a TNC-sized
  machine; a `PublishAot` sample in CI. Exit: every spec §9 target.
- **Plan 7 — preview.** An analyzer that reports the declaring-library diagnostics where modules are written; the
  code fixes (`SALCH0201`, `SALCH0207`, D24's `SALCH0901`/`0902` "Add phase" and the `SALCH0206` rename);
  `SALCH0801`; `Mermaid` and `Dot` constants; every docs sample compiled, the sample machine generated; the package
  built with the generator under `analyzers/` and checked in CI; the TNC 4.0 migration spec.
